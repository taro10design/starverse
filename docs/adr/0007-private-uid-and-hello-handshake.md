# 0007. 持ち主の鍵 uid は秘密にし、hello ハンドシェイクで持ち主 ID を作る

- 状態: 採用（日付 2026-10-17）

## 背景

星や線の持ち主は、端末が作る鍵 `uid` で決まる。最初の実装は、この `uid` を星の `by` にそのまま入れて、
`welcome` や `star` / `link` の配信で全員に送っていた。`uid` は「持ち主であることの証明」そのものなので、
他人の `by` を読めば、その人になりすませた（線を消す、星を動かす、上限の枠を使い切る）。
独立コードレビューで見つかった、重大な欠陥である。

## 検討した選択肢

- 各メッセージに `uid` を載せ、サーバーが毎回ハッシュして比べる
  - 利点: サーバーに状態が要らない。
  - 欠点: ハッシュ計算（`crypto.subtle`、非同期）がメッセージごとに走る。ログや中継点に `uid` が何度も流れる。
- 接続の最初に `hello {uid}` を 1 回だけ送り、サーバーが持ち主 ID を接続に固定する
  - 利点: `uid` が通信に流れるのは 1 回だけ。以降は接続が持ち主を覚えている。ハッシュも 1 回。
  - 欠点: hello が来るまで `welcome` を返せない。hello 前のメッセージの扱いを決める必要がある。
- 署名つきトークン（サーバーが発行して検証する）
  - 利点: `uid` を端末に作らせない。失効もできる。
  - 欠点: 発行の仕組みと鍵の管理が要る。個人開発の規模には重い（TODO に残す）。

## 決定

`hello {uid}` ハンドシェイクを採用する。

- クライアントは接続が開いたら最初に `hello {uid}` を送る。サーバーは `uid` を `UID_PATTERN`（`shared/limits.ts`）で検証し、
  合わなければ 1008 で切断する（切り詰めない）。
- 持ち主 ID は `SHA-256(uid)` の hex 先頭 32 文字（`server/src/identity.ts`）。接続に固定し、2 回目以降の hello は無視する。
  `StarData.by` / `LinkData.by` にはこの ID を入れる。`uid` は保存も配信もしない。
- サーバーは持ち主が決まってから `welcome`（`me` に持ち主 ID）を返す。クライアントは `star.by === me` で自分の星かを判定する。
- hello の前に届いたメッセージは無視する。hello が 10 秒以内に来ない接続は alarm で切る。ハッシュ計算の間に届いた分は
  最大 32 件まで貯めて、`welcome` のあとに順に処理する。
- 上限は持ち主 ID ごとに数える。持ち主は接続につき 1 つなので、1 接続が置ける星は 64 個まで。
  同じ IP からの接続は 1 つの空あたり 4 本までにする（IP はハッシュにして持つ。生の IP は保存しない）。

## 結果

- 良い点: 他人の `by` から `uid` は分からない。なりすましと、上限の枠の乗っ取りができなくなる。
- 良い点: `uid` が通信に流れるのは接続ごとに 1 回で、各メッセージが軽くなる。
- トレードオフ: 鍵リンク（`?key=<uid>`）を知る人は、その持ち主になれる。リンクの扱いは利用者に任せる。
- トレードオフ: 上限は接続・IP で縛るため、IP を変えられる攻撃者には効きにくい。根本の対策はエッジの
  Rate Limiting / WAF ルールに置く（[TODO](../TODO.md)）。
