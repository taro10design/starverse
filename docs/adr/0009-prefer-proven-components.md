# 0009. 自作を減らし、実績のある部品に置き換える

- 状態: 採用（日付 2026-10-17）

## 背景

独立コードレビューを 3 回行い、重大・高の指摘が 1 回目 6 件、2 回目 1 件、3 回目 1 件（直前の修正が生んだ退行）と続いた。
指摘の多くは、**自作した部分**にあった。

- Durable Object の接続管理とハイバネート復帰（`room.ts` の接続の再構築、`drop`、alarm の締め切り）
- クライアントの再接続の状態機械（二重接続、古い接続のイベント、half-open、バックオフの戻し方）
- 手書きの入力検証と、型の二重定義
- IP ごとの制限（接続数、接続頻度、星の上限、HMAC）

リアルタイム通信と認証まわりは、直すたびに新しい穴が見つかりやすい。「指摘 0」は現実的な目標にならない。
そこで、**実績のある部品に置き換えて、自作のコードを減らす**。コードが無くなれば、指摘の元も無くなる。

## 決定

- Durable Object を **PartyServer** の `Server` に載せ替える。接続の管理・ハイバネートからの復帰・broadcast は部品に任せる。
  残すのは、アプリ固有の部分（hello の握手、世界のルール、視界配信、満員の振り分け）。
- クライアントの接続を **PartySocket** に載せ替える。再接続・バックオフ・接続タイムアウトは部品に任せる。
  残すのは、hello の送信、死活監視の ping、隠れたタブの切断、サーバーが指示した送信間隔。
- メッセージのスキーマを **Valibot** で `shared/` に 1 か所で定義する。サーバーの入力検証と、型の導出に使う（手書きの検証と型の二重定義をやめる）。
- **IP に関する自作コードを削除する**（接続元の HMAC、同一 IP の接続数・接続頻度・星の上限）。IP ごとの制限は、エッジの
  レート制限ルールで行う。サーバーに残る防御は、接続ごとのトークンバケット、1 人あたりと全体の上限、混雑ペナルティ。
- `room.ts` を含むサーバーのテストを、**@cloudflare/vitest-plugin** で Workers ランタイム上で行う。

## 追記（2026-10-17、レビュー指摘を受けて）

エッジのルールを設定するまで、同じ接続元からの大量の接続を止めるものが無い、という指摘を受け、Worker の入口（`server/src/index.ts`、判定は `server/src/gateway.ts`）に次を足した。どれも部品（Workers のバインディング・PartyServer の API）を使う薄いコードで、自作の計数は持たない。

- **接続頻度**: Rate Limiting バインディング `CONNECT_LIMITER`（`wrangler.jsonc` の `ratelimits`、60 秒に 60 回、キーは `CF-Connecting-IP`。IPv6 は /64 ごと）。超えたら 429。上の表の「見送り」を改め、**使えなかったときに外せる形**で採用する（`wrangler.jsonc` の `ratelimits` を消せば、`env.CONNECT_LIMITER` が無くなり制限なしで動く）。公式資料のとおり場所ごとの近似で、エッジのルールの代わりではなく併用する
- **Origin の許可リスト**: `/ws` は `config.ts` の `ALLOWED_ORIGINS`（`uchu.pages.dev` とそのプレビュー、localhost / 127.0.0.1）と同じオリジンだけ。不許可は 403。Origin の無い接続（ブラウザ以外）は通す
- **`x-partykit-*` ヘッダーの除去**: PartyServer の内部用ヘッダー。クライアントが付けると props のデコード失敗でスタックトレースが返っていた
- 空の取得を `getServerByName` から `env.UNIVERSE.getByName` に替えた。PartyServer 0.5.10 は `this.name` を `ctx.id.name` から取り、`onStart` は最初の `fetch` の中で済ませるので、`setName` の RPC（1 往復）が要らない

## 追記（2026-10-17、4 回目のレビュー: 空の中の容量）

「少数の接続で、空の容量と星・線の枠を使い切れる」という指摘を受け、空（`server/src/room.ts`・`world.ts`）に次を足した。

- **同じ接続元（IP）の同時接続数**を空ごとに 32 本まで（`LIMITS.maxConnsPerIp`、超えたら 429。IPv6 は /64 ごと）。上の「IP の自作コードを削除する」を一部戻すが、前の実装とは違い**メモリ上だけ**で数える（IP は保存せず、接続の state にも入れない）。休止から起きると数え直しになるのは許容する（休止するのは誰も動いていないとき）
- **満員の判定と送信間隔の人数は、hello 済みの人だけ**で数える。hello 前の接続は別枠（`maxPendingConnections` = 20、超えたら 503 と `x-room-full` で次の空に回す。1 つの空の別枠を埋めても、サイト全体の新しい接続は止まらない）。hello 前の接続で満員にして正規の人を締め出すことができなくなる
- **部屋全体の新しい星・線の作成速度**を 1 分に 120 個（`maxNewStarsPerMinute` / `maxNewLinksPerMinute`）。持ち主ごとの 64 / 96 は据え置く。置き直しは数えない
- **受信量**: 受け取ったメッセージは処理しなくても課金される（ADR 0008）ので、サーバーが減らせるのは「指示を守らない接続を切る」ことだけ。指示した送信間隔の半分より短い間隔の位置（p）を直近 10 秒で 100 通数えたら 1008 で切る。速すぎる p も配信の対象にはする（配信は tick でまとめるので量は増えず、捨てると止まった位置が配られないことがある）。hello 済みの接続の読めない JSON・知らない t は違反として数える。トークンの回復量（毎秒 40）は人数で絞らない: なぞって星を置く操作（毎秒 20 個 = 40 トークン）と 10Hz の位置、続く 64 個の一括削除が、今の値でちょうど収まる（`server/tests/inbound.test.ts`）

**動かずに見ている人（無操作の member）は切らない。** 正規の閲覧者を切ることになるためで、上の対策で足りると判断した: hello 前の接続は締め切り（10 秒）と別枠で切れ、hello 済みの接続を増やすには接続頻度（60 秒に 60 回）と同時接続数（IP ごとに 32 本）の両方を越える必要がある。無操作の接続は位置を送らず、ping は自動応答で Durable Object を起こさないので、受信の費用も稼働時間もほとんど使わない。残る弱点は、多数の IP を使う相手（ボットネット）で、それはエッジのルールの領分とする

## 追記（2026-10-17、最終確認のレビュー: 正規の利用者を締め出さない）

- hello 前の接続の別枠があふれたら、次の空に回す（前は 503 で止めていたので、先頭の空の別枠を埋めるだけでサイト全体の新しい接続が止まった）
- 学校や会社の NAT の内側から大勢が同じ IP で入れるよう、同時接続を 32 本、接続頻度を 60 秒に 60 回に広げた
- IPv6 は /64 ごとに数える（末尾 64 ビットは端末が自由に変えられるため。`server/src/gateway.ts` の `addressKey`）

## 結果

- 良い点: 指摘の元になっていた自作コード（接続の再構築、再接続の状態機械、手書きの検証、IP の管理）が減る。
- 良い点: 実績のある部品が、既知の問題を直し続けてくれる。バグの報告先もある。
- トレードオフ: 依存が増える（PartyServer は 0.x。API が変わる可能性がある）。バージョンを固定し、Dependabot で追う。
- トレードオフ: IP ごとの制限はコードの外（Cloudflare の設定）に出る。設定しないと、1 つの IP から多数の接続ができる。
- 方針: 「自作は、使える部品が無いときだけ」（`research-reuse` スキル）。
