# 0006. 後方互換性は取らない

- 状態: 採用（日付 2026-10-17）

## 背景

このリポジトリは個人開発のポートフォリオで、外部の利用者や、保守を引き継ぐ他のチームはいない。
古い形式や非推奨の経路を残すと、読む量とテストの量が増え、設計の意図がぼやける。

## 検討した選択肢

- 互換を保つ（旧形式の読み込み、非推奨の経路、互換シムを残す）
  - 利点: 古いクライアントやデータが動き続ける。
  - 欠点: 分岐が増え、コードが読みにくくなる。削除のタイミングを決めにくい。
- 互換を取らず、古いものは削除する
  - 利点: 現在の形だけが残り、コードが小さく保たれる。
  - 欠点: 古いデータ・クライアントは動かなくなる。

## 決定

後方互換性は取らない。古い形式・非推奨の残置・互換シムは書かず、削除する。

移行コードも書かない。星の寿命は最長3時間なので、旧形式（`stars` / `links` キーに配列で保存）のデータは
捨てる。以前あった `migrateLegacy`（旧キーを 1 件 1 キーへ移す処理）は削除した。
本番の Durable Object のストレージに旧キーが残るが、読み込まれないので無害である。
空の名前 `space` を維持している（ADR 0001）のは、移行のためではなく、最初の空を従来の名前のまま使い続けるためである。

配信順序のずれ（Worker と Pages の同時デプロイ）で、一時的に新旧のクライアントとサーバーが
混ざる場合がある。許容し、ここに明記するだけにする。

## 結果

- 良い点: コードベースに現行の形式だけが残り、説明も短くて済む。
- 良い点: 新しい設計（ADR 0001〜0005）へ、移行の足かせなしに進めた。
- トレードオフ: 古いクライアントを開いたままのユーザーは、リロードするまで正しく動かないことがある。
- トレードオフ: デプロイ時に、本番の既存の星（最長3時間で消えるもの）が消える。
