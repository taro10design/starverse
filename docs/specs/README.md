# 仕様書（docs/specs）

新機能や挙動の変更は、実装の前にここへ「何を・なぜ」を書く。コードを書くのはその後。
決定の理由（なぜその設計にしたか）は [docs/adr/](../adr/README.md) に、ここには「何ができれば完成か」を書く。

## 書き方

1 本の仕様書は次の見出しで書く。

| 見出し | 書くこと |
| --- | --- |
| 目的 | 誰の、どんな困りごとを、なぜ解くのか。1〜3 文 |
| やらないこと | 意図して作らないもの。理由も一言 |
| 受け入れ条件 | テストできる 1 文ずつ。「〜できる」「〜のとき〜になる」の形。確認方法（自動テスト / e2e / 手動）を併記する |
| インターフェース | 画面・操作・メッセージ・設定値。数値は出どころ（ファイルと名前）を書く |
| リスク | 壊れうる点と、その時の振る舞い |

## 守ること

- 数値や挙動はコードから裏取りして書く。書かれていないことを作らない。コードを変えたら仕様書も同じ変更で直す。
- 受け入れ条件は、読んだ人が「できた / できていない」を判定できる文にする。「快適に」「適切に」は使わない。
- 自動テストが無い条件は、手動確認として [実機確認チェックリスト](../qa/device-checklist.md) の項目と対応づける。
- 番号は 4 桁の連番。取り下げた仕様書は消さず、冒頭に「廃止」と理由を書く。
